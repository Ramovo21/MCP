## Implemented

- Docker-compatible Web/Gateway/private Worker/Telemetry deployment, Caddy HTTPS configuration and external Supabase cloud connection settings. `/health` and `/ready` separate liveness from dependency/schema readiness. Application containers run as `node`, not root.
- Development/test/staging/production configuration examples and sanitized fail-fast validation. Staging requires HTTPS public origins, explicit allowed hosts and the private worker service.
- Asynchronous SecretProvider boundary, environment test provider, authenticated encrypted local file provider and deployment-module injection. Existing tenant-bound credential/token encryption remains supported. Cloud adapter guidance is included; no claim is made that managed KMS was integrated.
- HTTP Worker transport with private bearer authentication, bounded inputs/results, cancellation, hard child-process termination, worker health and unchanged durable execution claims. No automatic retries of ambiguous external writes.
- Real OTel SDK/exporter, Collector and Jaeger; correlated spans for request/auth/policy/approval/dispatch/worker/connector/upstream with measured duration and safe status/error metadata. Parent IDs persist for resumed executions. No automatic instrumentation of headers or URLs.
- One Google Workspace READ connector: Gmail search/get, Drive metadata search, Calendar event list. Per-service consent selection, PKCE, encrypted tokens, scope/provider/tenant checks, refresh, revocation and reconnect. Google OAuth cannot be attached to unrelated connector types. Search text is redacted in persisted execution arguments.
- Environment and worker health display, OAuth/connection status, account labels, test timestamps, reconnect/revoke actions and existing execution trace detail. New additive migrations record connection health and trace parents.
- Reproducible local runtime proof, Docker smoke and credential/history scan scripts. CI includes the new suites and local telemetry/recovery proof; remote GitHub Actions itself has not been run in this task.

## Failure tests and fixes

Google lifecycle tests use a local HTTP provider fixture, not Google accounts: expired access token refresh, omitted refresh scope, encrypted access/refresh storage, PKCE verifier exchange, tenant ownership, provider/connector mismatch, 401/403/429/500, timeout/recovery, reconnect and revoked authorization. Existing OAuth tests exercise simultaneous refresh claims and revocation during callback. Existing audit tests verify CRITICAL approval, rejection, concurrent duplicate decisions, no policy bypass, disabled/revoked tool access, API-key revocation, tenant isolation, SSRF, oversized results and crash/timeout classification. These are **local** failure tests; none is mislabeled as a staging Internet test.

Issues found and repaired while implementing/verifying:

1. A fresh Linux Docker build rejected an inferred exported Express type although the Windows check passed. Added an explicit `express.Express` return type and rebuilt successfully.
2. Idle PostgreSQL connection errors could terminate Node during an outage. Added a sanitized pool error listener; a real TCP interruption now makes readiness fail while liveness survives, then recovers.
3. Inspector's previous global sign-out revoked other sessions of the test account. Changed it to local-session sign-out and verified Gateway restart/idempotency afterward.
4. OAuth refresh responses may omit `scope`; the provider now distinguishes omission and retains the prior grant. Every required tool scope is still enforced server-side.
5. Provider-neutral OAuth initially allowed Google authorization on unrelated connections. Added provider-declared connector binding, plus an explicit negative regression assertion.
6. Sensitive Gmail/Drive search text is marked for redaction; tests verify it is not persisted in cleartext arguments.
7. During test development, the temporary PostgreSQL proxy accidentally looped to its own rewritten port. Stopped only task-owned processes, fixed the original destination capture and reran the recovery proof. An incorrect test method name and misplaced React state were also fixed before final validation.
8. A final manual Inspector attempt ran immediately after restarting localhost Gateway and exited before startup completed. After `/ready` returned `ok`, the same `pnpm test:inspector:live` command passed tools/list and tools/call. Automated service proof already waits for readiness. The Docker smoke script also needed explicit Node-global declarations to pass ESLint; the final complete validation passed after that correction.

Nonblocking output observed: Next.js warns that its optional ESLint plugin is not configured; repository ESLint and Next production builds pass. Docker dependency download had a transient retry and recovered. The pre-existing optional local Supabase Vector container restarts; the new Collector/Jaeger pipeline was separately verified. This is not a certification of the older analytics stack.

## Security and remaining blockers

Gateway remains the sole public execution entry point. Private Worker requests require a service credential; approved executions still require an atomic database claim. Tenant-scoped queries/RLS and permission tests continue to pass. OAuth tokens and credentials remain authenticated-encrypted; API keys remain hashed. Provider 401s mark only the used authorization as requiring reconnect; reconnect races do not overwrite newer credentials. Logs/traces omit headers, credentials and payloads. The implementation does not promise exactly-once external effects without upstream idempotency.

Before public staging can be verified, supply an authorized deployment host/account, dashboard/Gateway DNS names, a Supabase cloud project with migrations and Auth URLs configured, and a Google OAuth web client plus consenting test user. Keep secrets in local files/secret-manager injection, not chat. Google restricted-scope verification/consent-screen requirements must be resolved for intended users.

Remaining production risks: trusted connectors share an OS/database trust boundary despite crash isolation; use least-privilege database identities and container/egress policies. Use TLS/mTLS between services across hosts. Configure a real managed secret adapter and rotation, persistent authenticated telemetry/retention, image vulnerability review/digest pinning, backups and restore drills, deployment rollback and HA. Current fixed Google tool names permit one published Google namespace per organization; account names are operator-supplied labels. Full-email responses remain subject to the 2 MiB safety limit. Google partial-grant/account-policy behavior still needs real consent testing.

## Exact local reproduction

Requires Node >=22.19 (tested 24.18), pnpm 10.32.1 and Docker. No database reset is needed.

```sh
pnpm install --frozen-lockfile
pnpm db:start
pnpm env:local
pnpm db:migrate
pnpm db:seed
pnpm verify
pnpm test:live
pnpm test:audit
docker compose -f docker/compose.telemetry.yml up -d
pnpm test:staging:local
pnpm dev
# In another terminal once Web/Gateway are ready:
pnpm test:inspector:live
pnpm test:e2e
node --env-file-if-exists=.env scripts/scan-secrets.mjs
```

The seed procedure generates/preserves local environment settings; use the account configured by `SEED_EMAIL` and the unique `SEED_PASSWORD` in ignored `.env`. No shared plaintext password is published. To run the service boundary manually, set matching `WORKER_AUTH_TOKEN`, `WORKER_URL=http://127.0.0.1:4100` and start `pnpm dev:worker` before `pnpm dev`. Default local mode still uses private child processes directly.
